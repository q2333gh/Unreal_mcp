# 工具系统与调度原理（Tooling Internals）

## 1. Tool Registry 的真实角色
`ToolRegistry` 不是简单注册表，而是“协议入口控制器”，核心职责包括：
- 向 MCP 声明工具列表与能力。
- 接收 `call_tool` 请求并执行统一错误处理、响应校验。
- 与动态工具开关系统联动（listChanged 通知）。

该设计让 Tool 的运行时可见性（是否展示给 client）与调用执行（handler）可以独立演进。】.【F:src/server/tool-registry.ts†L1-L14】【F:src/server/tool-registry.ts†L45-L79】

## 2. 动态工具管理（Runtime Feature Gating）
`DynamicToolManager` 将每个工具维护为 `ToolState`（name/category/enabled），并维护 category 统计。

支持能力：
- 按工具启停
- 按分类启停
- 保护工具不可禁用（如 `manage_tools`, `inspect`）
- 查询当前状态（总数、启用数、禁用数）

这使 server 能针对不同 MCP 客户端/场景做“能力裁剪”。】.【F:src/tools/dynamic-tool-manager.ts†L10-L28】【F:src/tools/dynamic-tool-manager.ts†L31-L67】【F:src/tools/dynamic-tool-manager.ts†L132-L173】

## 3. 客户端能力协商与 list_changed
`ToolRegistry` 中有对客户端能力库 `mcp-client-capabilities` 的检查逻辑，会按 client 名判断是否支持 `tools.listChanged`，并在分类切换时主动发通知。】.【F:src/server/tool-registry.ts†L44-L79】【F:src/server/tool-registry.ts†L99-L110】

这体现了 MCP 协议层面的“**服务端主动通知**”模式：不是每次都被动等待 `list_tools`。

## 4. Consolidated 模式的关键价值
在 `consolidated-tool-handlers.ts` 中，绝大多数工具都采用“`tool + action`”分发：
- 对外：工具名数量可控，schema 和文档集中。
- 对内：action 可扩展，甚至支持旧 action 到新 action 的映射。
- 兼容：弃用 tool 可保留代理入口，避免客户端一次性断裂。

因此这是典型的“**协议面收敛、执行面扩散**”设计。】.【F:src/tools/consolidated-tool-handlers.ts†L57-L116】【F:src/tools/consolidated-tool-handlers.ts†L163-L216】

## 5. 发送请求前的三层防线
所有标准 handler 最终会调用 `executeAutomationRequest()`，该函数提供三层防线：

1. **参数存在性与 action 检查**（防止空请求）
2. **安全模式检查**（阻断 `../`、`/etc/`、Windows 系统路径等）
3. **桥接可用性检查**（函数存在 + 连接状态）

这样可在 TS 层提前拦截高风险输入，避免 UE 侧承担全部校验成本。】.【F:src/tools/handlers/common-handlers.ts†L6-L52】【F:src/tools/handlers/common-handlers.ts†L70-L124】

## 6. 我认为最关键的工程原则

- **接口稳定优先**：兼容映射与 deprecated 转发保留生态稳定。
- **最小权限输入**：限制路径前缀、拦截 traversal。
- **控制面可调**：通过动态启停工具构建可运营能力面板。
- **协议感知实现**：根据客户端差异决定是否发送 listChanged。
