# Unreal MCP 服务整体架构总览（深度版）

## 1. 系统定位
该仓库实现的是一个面向 Unreal Engine 5 的 MCP Server：上层对外暴露 MCP 协议工具（Tool），下层通过 WebSocket 与 UE 编辑器插件通信，把“工具调用”转成“引擎内自动化动作”。整体是**双进程架构**：

- **Node.js/TypeScript 进程**：MCP Server 入口、工具注册、参数校验、响应标准化、动态工具管理。
- **Unreal Editor C++ 插件进程内子系统**：接收请求、在 Game Thread 调度并调用原生 UE API。

入口由 `src/index.ts` 创建 MCP `Server`、`UnrealBridge`、`AutomationBridge`，并注册工具/资源。.【F:src/index.ts†L1-L158】

## 2. 启动分层与职责边界

### 2.1 入口层（进程级装配）
`createServer()` 负责组装核心组件：
- 桥接层：`UnrealBridge` + `AutomationBridge`
- 运维层：`HealthMonitor`、metrics server、GraphQL server
- 能力层：WASM 初始化、响应 schema 校验注册
- MCP 层：实例化 `Server` 并交给 `ServerSetup` 注册资源与工具

这使得“连接、观测、能力、协议”四层在启动时解耦。.【F:src/index.ts†L69-L158】

### 2.2 装配层（注册资源与工具）
`ServerSetup` 在 `setup()` 中完成：
1. 环境校验（`UE_PROJECT_PATH`、`UE_ENGINE_PATH`）
2. 资源注册（Asset/Actor/Level）
3. 工具注册（ToolRegistry）
4. 惰性连接策略（`ensureConnectedOnDemand`）

关键点：服务并不强制启动即连接 UE，而是按需连接，降低启动失败面。.【F:src/server-setup.ts†L42-L110】

## 3. 请求主链路（从 MCP 到 UE）

### 3.1 MCP 调用入口
`ToolRegistry` 注册 `ListToolsRequestSchema` 与 `CallToolRequestSchema`，并把工具调用转发到 consolidated handlers（`handleConsolidatedToolCall`）。这保证了对外协议统一，对内实现可演进。.【F:src/server/tool-registry.ts†L1-L14】

### 3.2 统一路由层（Consolidated Handlers）
`consolidated-tool-handlers.ts` 中通过 `toolRegistry.register()` 对各大工具域（资产、蓝图、关卡、动画、系统等）分发，并支持：
- 历史 tool 名兼容映射（例如旧名字重定向）
- action 归一化与图编辑 action 映射
- 已弃用入口兼容（一次性 deprecation warning）

这是一种“**稳定外观 + 内部重组**”的架构手法。】.【F:src/tools/consolidated-tool-handlers.ts†L57-L156】【F:src/tools/consolidated-tool-handlers.ts†L163-L238】

### 3.3 自动化桥发送层
几乎所有真正落到 UE 的动作最终通过 `executeAutomationRequest()` 发出。此函数做了三件关键事：
1. 安全检查（路径穿越、非法绝对路径）
2. 连接状态检查（未连通直接报错）
3. 超时参数剥离与请求发送（防止 client-only 参数泄漏到引擎端）

这体现了“**发送前统一收口校验**”的原则。】.【F:src/tools/handlers/common-handlers.ts†L14-L52】【F:src/tools/handlers/common-handlers.ts†L95-L124】

## 4. C++ 插件执行层设计

### 4.1 子系统初始化
`UMcpAutomationBridgeSubsystem::Initialize` 完成连接管理器创建、消息回调绑定、handlers 初始化、ticker 注册；并在 commandlet（cook/package）模式下主动跳过，避免构建流程受影响。】.【F:plugins/McpAutomationBridge/Source/McpAutomationBridge/Private/McpAutomationBridgeSubsystem.cpp†L77-L122】

### 4.2 Game Thread 与安全状态守护
`ProcessAutomationRequest` 明确保证在 Game Thread 执行；若遇到 `Saving/GC/AsyncLoading` 则排队延后；同时带有重入保护与 pending 队列二次调度。这个机制降低了编辑器高风险状态下崩溃概率。】.【F:plugins/McpAutomationBridge/Source/McpAutomationBridge/Private/McpAutomationBridge_ProcessRequest.cpp†L11-L76】【F:plugins/McpAutomationBridge/Source/McpAutomationBridge/Private/McpAutomationBridge_ProcessRequest.cpp†L86-L147】

## 5. 可观测性与稳定性机制

- `HealthMonitor` 维护请求成功率、平均响应时间、错误窗口、连接状态。
- 健康检查使用安全无副作用命令（`stat none`），并有“长时间无成功则暂停”策略防止噪音与资源浪费。

这是“**低侵入健康探测**”+“**退避降噪**”组合。】.【F:src/services/health-monitor.ts†L4-L33】【F:src/services/health-monitor.ts†L66-L117】

## 6. 架构核心原理总结

1. **分层清晰**：协议层（MCP）与执行层（UE）以桥接层隔离。
2. **集中路由**：consolidated handlers 统一工具面，降低接口碎片化。
3. **统一安全前置**：请求出站前做参数与路径安全检查。
4. **线程与状态优先**：C++ 侧严格 Game Thread 调度 + Unsafe State 排队。
5. **按需连接与观测闭环**：惰性连接 + health/metrics 提升运行鲁棒性。
